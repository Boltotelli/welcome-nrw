# SSL read permission in the leadership dashboard

SSL is part of the normal leadership dashboard and uses the original shared FightClub map (`createFightClubMap` and `swordBackdrop`). No second guest interface is used. `leitung/ssl.html` only redirects old links to the dashboard. The former guest view script/styles and separate API route are retired.

Owners manage the independent permission **SSL · nur lesen** in the normal account dropdown under Allianz & Rechte. Guest accounts appear there with their display name. For a guest, only the SSL read permission and account enabled checkbox are editable; the API rejects attempts to give that identity other module rights. Regular R4/R5 accounts may also receive SSL read permission without full FightClub permission. Full FightClub continues to authorize editing SL, TriAlliance and SSL.

The guest creation panel remains for creating an external identity without an NRW game membership or R4 rank, resetting a password and disabling the identity. New credentials point at the common leadership login. Existing guest identities, names and passwords are preserved. `ssl_read` defaults to true for the existing viewer rows; no Auth account is recreated. There is no automatic creation of real guest accounts at deployment.

All accounts use the normal leadership auth session. The staff gate validates the Auth user and either an existing authorized staff record or an enabled SSL viewer record with SSL read permission. Anonymous users and user metadata cannot grant access. The guest bootstrap returns only public alliance presentation, the SSL-only role and minimal planned SSL player profiles. It never loads transfers, staff directories, player dossiers, notes or other internal modules. SSL-only sessions allow bootstrap GET and `fightclub_data` POST; every other protected mode/action is rejected before its handler. Membership and Auth permissions are not expanded.

The read-only FightClub payload uses explicit field allowlists and event `swordland_summit`. Notes and no-show markers are never selected. Only profiles referenced by SSL assignments are returned. Guests can choose dates, legions and objectives and copy names and team messages. There are no assignment, save, automatic planning, player lookup, profile or leader-edit controls. The same original map implementation serves both editors and readers. Defensive UI guards also ignore forged mutation controls; the API remains authoritative.

Schema upgrade: `docs/ssl-dashboard-permission.sql` adds the separate `ssl_read` permission to the existing RLS-protected viewer table. Existing service-role-only grants and policies stay unchanged. Deploy `index.ts`, `fightclub-ssl.ts` and `ssl-access.ts` together before the static UI. `verify_jwt:false` is unchanged; requests are still authenticated manually with `getUser` and live database permissions.

Tests: `tests/ssl-dashboard-api.cjs` executes the real staff gate, bootstrap, read handler, write handlers and dispatcher with isolated data. It covers guest and R4 SSL-only rights, revoke of existing sessions, omission of private fields and denial of other modules/actions. `tests/ssl-login.cjs` uses Playwright against the actual app login, shared map, copy actions, mobile layout and owner permission form. Previous guest access test filenames delegate to these replacements. Existing SSL planning and map regression suites still pass.
